# ストックサイクルアプリ 要件定義書

作成日: 2026-08-15

## 1. 概要・目的

レシート写真をアップロードするだけで、AI（OCR + LLM）が購入履歴を学習し、トイレットペーパーや洗剤などの日用品消耗品について「そろそろ次を買うタイミング」をLINEでリマインドしてくれるアプリ。

| 項目 | 内容 |
|---|---|
| 利用者像 | 家族で共有（夫婦＋子供3人）。全員同等の権限で利用 |
| 対象商品 | 日用品全般（トイレットペーパー、洗剤など消耗品） |
| 学習方式 | レシートOCRによるフル自動学習 |
| MVPスコープ | OCR自動学習込みのフル版 |
| 副次的な位置づけ | Takashiさんの転職活動における個人開発ポートフォリオ（AWS構成を面接で説明できる事例）としても意識する |

## 2. 主要機能一覧（MVP）

- レシート写真のアップロード（スマホカメラでの即時撮影／ギャラリーからの選択、両対応）
- OCRによる商品名・数量・購入日の自動抽出
- 抽出結果の確認・修正UI（OCRの誤読を前提に必須機能とする）
- LLMによる商品名の名寄せ（表記ゆれ吸収）とカテゴリ推定
- 購入サイクルの自動推定（2回目の購入から仮推定を開始）
- 在庫一覧画面（次回購入予想日が近い順のリスト表示）
- レシートがない場合の手動登録機能（商品名・購入日を直接入力）
- LINEでのリマインド通知（Flex Message、リッチ形式）
- 家族共有機能（誰でも追加・編集可能、権限差なし。MVPでは最初に登録した固定メンバーのみを想定し、メンバーの追加・招待フローは対象外）
- LINEログイン連携によるユーザー認証
- アイテムごとのトラッキングON/OFF切り替え（在庫一覧・サイクル推定の対象から個別に除外できる。OFFにしたアイテムは「非トラッキング」として一覧下部に残り、いつでも再度ONにできる）
- アイテムごとのアラートON/OFF切り替え（トラッキングはするが通知だけ止めたい、というケースに対応。グローバルな通知タイミング設定とは独立して、アイテム単位でミュートできる）

## 3. ユーザーフロー

### 3.1 オンボーディング（初回設定）
1. LINE公式アカウントを友だち追加
2. アプリ側で連携コードを発行し、LINEアカウントとアプリアカウントを紐付け

### 3.2 レシート登録〜学習
1. スマホカメラで即時撮影、またはギャラリーから画像を選択してアップロード
2. AWS TextractでOCR解析（商品名・数量・購入日を抽出）。かすれ・破損等でOCRが商品情報を取得できなかった場合は、確認・修正画面には進まず、自動的に手動入力画面へ遷移する
3. LLM（Bedrock等）で商品名を正規化し、カテゴリを推定
4. ユーザーが抽出結果を確認・修正
5. 2回目の購入データが揃った時点から、仮の購入サイクルを推定開始（以降、データが増えるほど精度向上）

※ 同一レシートの重複アップロード検出（誤って2回登録してしまった場合の警告）はMVPでは対応しない

### 3.3 在庫確認〜リマインド
1. 在庫一覧画面で、次回購入予想日が近い商品から順に表示。各アイテムには「トラッキング」「アラート」の2つのトグルを表示し、その場でON/OFFを切り替えられる
2. トラッキングをOFFにしたアイテムは一覧から外れ、画面下部の「非トラッキング」セクションにまとめて表示される（いつでも再ON可能）
3. 予想購入日の2〜3日前に、トラッキングON かつ アラートON のアイテムのみを対象に、その日にリマインド対象となった商品をまとめて1通のLINE Flex Messageで通知
4. 通知には「買った」アクション用のボタンを含めるが、実際の購入報告はアプリ内画面で行う（ボタンはアプリの該当画面へのディープリンクとし、報告後は次回サイクルの起点としてリセットする）
5. 通知への未対応時の再通知は、MVPでは行わない（1回のみ）

## 4. データ設計・学習ロジック

| 項目 | 方針 |
|---|---|
| OCRエンジン | AWS Textract（Analyze Expense API） |
| 商品名の名寄せ | LLM（Amazon Bedrock等）による正規化＋カテゴリ推定。ユーザーは必要に応じて修正可能 |
| 購入サイクル推定 | 直近の購入間隔を重視した加重移動平均。生活の変化（子供の成長など）に追従しやすくする |
| 推定開始条件 | 同一商品の購入が2回記録された時点から仮推定を開始 |
| 外れ値対応 | 異常に短い／長い購入間隔（買いだめ・買い忘れ等）を検出し、推定計算から除外する |
| ブランド変更の扱い | 商品名単位ではなくカテゴリ単位（例：「トイレットペーパー」）でサイクルを管理する。ブランドを変えても同一商品として学習を継続する |
| 季節性・イベント消費への対応 | 個別のロジックは設けず、既存の外れ値除外ロジック（異常に短い間隔の除外）で吸収する |
| 金額・支払い情報の扱い | OCR抽出結果のうち金額・支払い方法（クレジットカード下4桁など）は最初から保存しない。保持するのは商品名・数量・購入日のみ |

## 5. LINE通知仕様

| 項目 | 方針 |
|---|---|
| 通知タイミング | 次回購入予想日の2〜3日前（全アイテム共通のグローバル設定） |
| 通知対象の絞り込み | トラッキングON かつ アラートON のアイテムのみを通知対象とする（アイテムごとにミュート可能） |
| 通知言語 | 英語に統一（UIと同じく、渡米後の実運用を前提とする） |
| メッセージ形式 | LINE Flex Message（リッチ形式、ボタン付き） |
| 複数商品の扱い | 同日にリマインド対象となった商品は1日1回にまとめて通知 |
| 再通知 | MVPでは不要（1回のみ通知） |
| 連携方式 | LINE公式アカウント（Messaging API）＋ LINE Login |

## 6. 非機能要件

| 項目 | 方針 |
|---|---|
| レシート画像の保存 | OCR処理後30日で自動削除。学習に使った構造化データ（商品名・数量・購入日）のみ保持し、個人情報を含む元画像は残さない |
| 対応デバイス | スマホブラウザ中心のレスポンシブWeb（ネイティブアプリは作らない。将来的なPWA化は検討余地あり） |
| 認証方式 | LINEログイン連携 |
| コスト方針 | 可能な限りAWS無料利用枠内での運用を目指す（個人開発規模を想定） |

## 7. AWS技術スタック案

Takashiさんの得意領域（Lambda、API Gateway、ECS Fargate、CloudFormation、CI/CD）を活かしつつ、転職活動時のポートフォリオとして説明しやすい構成を意識。

| レイヤー | 想定サービス |
|---|---|
| フロントエンド | React（Next.js）。S3 + CloudFrontでの静的ホスティングを想定 |
| API | API Gateway + Lambda（サーバーレス構成） |
| OCR | AWS Textract（Analyze Expense API） |
| 商品名寄せ・カテゴリ推定 | Amazon Bedrock（LLM） |
| データストア | DynamoDB（ユーザー・商品マスタ・購入履歴・サイクル推定結果） |
| 画像ストレージ | S3（ライフサイクルポリシーで30日後に自動削除） |
| リマインドバッチ | EventBridge Scheduler + Lambda（日次で予想購入日をチェックし、LINE Messaging APIへ通知送信） |
| 認証 | LINE Login（必要に応じてトークン管理にCognitoを併用） |
| IaC | AWS CDK（TypeScript） |
| コスト監視 | AWS Budgets（月額アラート、例: $5超過で通知） |
| 監視・運用 | MVPではCloudWatchのデフォルトメトリクス・ログのみ。個別のアラーム設計やTextract/Bedrock障害時のフォールバック（DLQ等によるリトライ）は将来課題とする |
| ポートフォリオ観点 | アーキテクチャ図・READMEを整備し、面接で構成の意図を説明できる形にする |

### 7.1 コスト試算（家族規模利用時、月あたり）

家族利用（週5〜20枚程度のレシートアップロード、リマインドバッチ1日1回）を想定した場合の概算。

| サービス | 想定コスト | 理由 |
|---|---|---|
| CloudFront | ¥0 | Always Freeティア（恒久無料）：1TB転送＋1,000万リクエスト/月まで無料。到達しない想定 |
| Lambda | ¥0 | 常時無料枠：100万リクエスト＋40万GB秒/月に収まる |
| DynamoDB | ¥0 | 常時無料枠：25GBストレージ＋25RCU/25WCU |
| EventBridge Scheduler | ¥0 | 1日1回のバッチのみ。無料枠1,400万回/月に対して誤差レベル |
| S3（画像保存） | ほぼ¥0 | 30日で自動削除する設計のため容量が積み上がらない |
| API Gateway | ¥0〜数十円 | 新規アカウントは12ヶ月無料。以降もHTTP API利用なら$1/100万リクエストと安価 |
| Textract（AnalyzeExpense） | **$2〜8/月（約300〜1,200円）** | 常時無料枠なし。$0.01/ページ。唯一の主要コストドライバー |
| Bedrock（Nova Micro） | 数十円/月未満 | 商品名寄せの短いテキスト処理のみのため、1回あたり1円未満 |
| **合計目安** | **月あたり数百円〜1,000円程度** | 実質Textract利用量にほぼ比例 |

> コストが気になる場合は、Bedrockのモデルを低コストなNova Microに固定する、AWS Budgetsで閾値アラートを設定する、といった対策で想定外の増加を防ぐ。

## 8. 成功指標（受け入れ基準）

| 指標 | 目標 |
|---|---|
| 購入サイクル予測精度 | 実際の購入日と予測日の差が平均±3日以内に収まることを目標とする |

## 9. 今後の検討事項（スコープ外・将来課題）

- 家族内での権限分け（子供アカウントの制限など）
- 家族メンバーの追加・招待フロー（招待リンク/QR発行など）
- 通知の再送・スヌーズ機能
- 商品ごとのリマインドタイミング個別設定（現状はON/OFFのみ、日数のカスタマイズは未対応）
- 通知言語のユーザー選択（英語・日本語の切り替え）
- 同一レシートの重複アップロード検出
- 詳細な監視・アラーム設計、障害時のフォールバック（DLQによるリトライ等）
- ネットスーパー等の外部購買サービスとの連携
- PWA化・プッシュ通知対応
